# Durable batch orchestration and explicit recovery

Scope: continuation cycle2026-10-12-live-batch-02, round3. Live source remains disabled until evidence gates pass. This does not alter account/lifetime caps, source entitlement requirements, or the five-round stop.

Authenticated POST /api/v1/batches accepts kind and request plus UUID Idempotency-Key. Complete admission precedes parent SDK startup. Startup failure returns the already-admitted batch ID with start_retry_required; the UI retains the frozen request and same key. Ambiguous persistence/server/network failures never authorize discarding that key. Explicit definite budget/query/live-disabled rejection can permit revision. GET status/results only reads; language, hover and chart interactions do not submit queries.

The parent Workflow persists only batch ID; its step returns only a boolean. Child SDK starts use only opaque job ID. Parent work does not consume an upstream concurrency slot; at most two active child executions are advanced, and existing global provider-capacity fencing still limits supplier execution to two. The server validates owner membership and immutable admission slots. No database lock crosses SDK IO. The parent checks five-second ticks within a15-minute admission lifetime; immutable original accounting month is checked at dispatch. Expiry cancels active children, conservatively marks parent uncertain and releases only untransferred operation holds. Transferred/ambiguous charges remain reserved. Completed parents release remaining untransferred holds once; full source verification is not implied by partial status.

SDK startup acknowledgements can precede database acknowledgement. Durable startup claim and actual execution fencing prevent duplicate parents/children from creating duplicate provider dispatch. Missing SDK state or observation timeout is not stopped execution. An explicit same-key POST may replace a parent only with authoritative failed/cancelled SDK status. Child runtime recovery reuses the same job only when every provider record is still reserved with no run ID. It keeps immutable call/slot/account reservations; the new current job lease adopts the existing undispatched call lease before HTTP. Any possibly dispatched child is marked uncertain for reconciliation, never automatically replayed. Persistent DB errors after two step retries can require explicit same-batch recovery. Local SDK restart durability for this new parent has not yet been demonstrated by the real-process recovery harness; existing single-job evidence is distinct.

Production UI retains owner/kind-scoped recovery pointer locally. Browser storage failure stays visible even after202. Signout/owner changes fence callbacks and clear visible private results. Whole-batch ceiling is explicitly chosen (defaultUSD0.10, maximumUSD0.50); actual remaining account limits may be lower. Arrival-window meeting covers target−2 through target departures; fixed-departure mode is explicitly selected. Results disclose one verification branch per query. Additional source candidate branches and source-confirmed arrival/baggage/fare evidence remain pending, so this is not a complete live recommendation acceptance claim.
